# MTG準備

会議前に関連情報を自動収集し、準備資料を生成する。
通常MTG・キックオフMTGは「顧客共有セクション」と「社内メモセクション」の2部構成。
1on1 MTGはメンバーの成長記録ベースの専用フォーマットで出力する。

## 使い方

`$ARGUMENTS` にMTG名またはメンバー名を指定できる。

- MTG名指定 → そのMTGを対象
- メンバー名指定（例:「Aさんとの1on1」）→ そのメンバーとの1on1を対象
- 「次のMTG」→ カレンダーの直近予定
- 未指定 → 今日・明日の予定一覧から選ぶ

## 手順

1. 対象MTGを特定する（指定あり→そのMTG／「次のMTG」→カレンダー直近／未指定→今日・明日の一覧から選択）
2. カレンダーから詳細を取得する: 参加者・場所・会議リンク・アジェンダ（通常は予定の検索結果にそのまま含まれる。個別取得が必要な場合だけ別途取得する）
3. **MTGタイプを判定**（下記）し、読み込む reference を決める
   - **1on1** → [1on1-flow.md](references/1on1-flow.md) を読む（質問カタログは [1on1-questions.md](references/1on1-questions.md)、設計理論は [1on1-principles.md](references/1on1-principles.md) を必要な時に）
   - **通常／キックオフ** → [meeting-formats.md](references/meeting-formats.md) を読む
4. **情報収集** — 以下を実行し、結果（件数）を控える（手順5の「情報源カバレッジ表」に必須）

   | # | 情報源 | やること | ゼロ件のとき |
   |---|---|---|---|
   | 1 | 議事録ツール | Circlebackなどの会議録音・要約ツールを会社名・人名で検索（無ければ議事録テキストを貼ってもらう） | 「該当0件」と記録する（新規の相手ならそれ自体が情報） |
   | 2 | チャット | Slack／Teams等を会社名・人名・会議名で検索。ヒットしたら前後の文脈も読む（LINEなど読み取れないものは貼ってもらう） | 同上 |
   | 3 | メール | Gmail／Outlookを参加者アドレス・会社名で検索 | 同上 |
   | 4 | 手元のファイル | `context/`・`work/` 配下を会社名・人名で検索 | 同上 |
   | 5 | 顧客台帳・タスクDB | Notionなどのデータベースがあれば検索 | 同上 |
   | 6 | Web | 会社概要・直近ニュース（詳細は [meeting-formats.md](references/meeting-formats.md) の「Webリサーチ」節。重ければ別タスクに分けてもよい） | |

   ⚠️ **ツールの認証エラーや「使えない」という警告が出ても、その情報源を黙って諦めない。** 別の経路（別のログイン方法、Web版、本人に直接貼ってもらう）を1回試してから「使えなかった」と書く。警告に押し流されて、調べたつもりで実は調べていないケースが起きやすい
5. 出力構成に従って資料を生成する（通常／キックオフは下記の「出力の2部構成ルール」を厳守。1on1は [1on1-flow.md](references/1on1-flow.md) の出力構成に従う）。**社内メモの末尾に「情報源カバレッジ表」を必ず入れる**（下記）
6. 保存する。通常/キックオフ: `work/mtg/YYYYMMDD_[会議名]_準備資料.md`、1on1: `work/mtg/YYYYMMDD_1on1_[メンバー名].md`（保存先はCLAUDE.mdに別の指定があればそちらを優先）

## MTGタイプ判定

- **1on1 MTG**: 会議タイトルに「1on1」「1 on 1」「ワンオンワン」を含む、または参加者が自分とメンバー1名だけの場合
    - → **1on1専用フロー**（[1on1-flow.md](references/1on1-flow.md)）に分岐する。通常の2部構成は使わない
- **通常MTG**: 定例・進捗・商談など
- **キックオフMTG**: 「キックオフ／KO／初回／プロジェクト開始」等のキーワード、または案件が「新規」ステータスの場合
    - 追加収集: 顧客台帳があれば契約条件・取引履歴を確認する

## 出力の2部構成ルール

通常MTG・キックオフMTGのファイルは必ず以下の2セクションに分けて出力する（1on1は対象外）。

### 【前半】顧客共有セクション（ここまでは相手に見せてOK）

お客さんにそのまま共有できる内容のみ。以下を守ること。

含めてよい情報:

- 基本情報（日時・参加者・場所・会議リンク）
- アジェンダ案（**冒頭に「先回り提案1本」を必ず置く** — 下記「先回り提案」参照）
- 前回MTGの振り返り（事実ベースの決定事項・合意内容のみ）
- 双方のアクションアイテム状況（事実のみ）
- 今回の確認・議論ポイント（中立的な表現）
- メモ欄

絶対に含めてはいけない情報:

- 金額・単価・コスト情報（自社の見積もり・原価・予算感）
- 社内の営業戦略・交渉方針（「強引に売り込まず」「関与度を高める」等）
- 相手先担当者の内部評価（「進行力が不足」「話しやすい」等）
- 社内ファイルパス（`work/`、`context/` 等のローカルパス）
- 社内ツールの参照（チャットのスレッドURL、メッセージID等）
- 「ミスマッチ」「見送り」等のネガティブな過去経緯の生々しい記述
- 飲み会・関係構築の戦術メモ
- 自社メンバーの役割・評価に関する内部メモ

表現のルール:

- 過去の経緯は「前回のお打ち合わせで〇〇を合意」のように中立的・事実ベースで書く
- ヒアリング事項は「ご確認事項」として丁寧に
- 確認ポイントは双方にとって有益な表現にする

### 先回り提案（1本必須・通常/キックオフMTGのみ）

**顧客接点1回につき、こちらから出す提案を最低1本入れる。** 先方の宿題確認と進捗報告だけの資料にしない。

- **置き場所**: 顧客共有セクションの「本日のアジェンダ案」の**冒頭**に1項目として置く。末尾に付け足さない
- **ネタの優先順位**: ①3ヶ月後に相手が困りそうなことの先出し ②見えているリスクの指摘 ③業界ニュース・他社の匿名事例からの示唆
- **金額・単価・見積もりは顧客共有セクションに書かない**（2部構成ルールのとおり）。提案の狙い・想定反論・価格感は社内メモの「先回り提案の裏側」に書く
- **1本も作れなかった場合は黙って省かない**。社内メモに「先回り提案なし」と理由（情報不足・関係フェーズが早い等）を明記する
- **線引き**: 速さを出すのは**議題設定**であって**理解**ではない。相手を置き去りにすると「よくわからないまま進んでいる」＝離脱シグナルになる。提案は1本に絞り、詰め込まない
- 1on1（社内メンバー）は対象外

### 【後半】社内メモセクション（社外秘）

`---` 区切り線の後に `## 【社外秘】社内メモ` ヘッダーで開始する。
以下の情報をここにまとめる。

- 営業戦略・交渉方針
- **先回り提案の裏側**（狙い・想定反論・価格感／1本も出せなかった場合はその理由）
- 料金・コスト情報（見積もり・単価・予算感）
- 相手先担当者の人物メモ（性格・傾向・関係構築のコツ）
- 関係構築のアプローチ
- 内部の準備タスク・チェックリスト
- 社内ファイルパス・社内ツールの参照リンク
- リスク・懸念事項（社内視点）
- 過去の経緯の率直な記録（ミスマッチ・見送り等）
- **情報源カバレッジ表（必須・下記）**

#### 社内メモにも書いてはいけないもの（機密の二段構え）

「社外秘だから社内メモに書けばよい」ではない。**対外共有の可否と、保存・記録してよいかどうかは別のルール**で、後者のほうが厳しいことがある。

| 情報 | 顧客共有セクション | 社内メモ | ファイルへの記録 |
|---|---|---|---|
| 顧客名・金額・単価 | ✗ | ✓ | ✓（自社の非公開領域のみ） |
| **セキュリティ上の弱点・システムの欠陥の技術詳細** | ✗ | **✗** | **✗（記録自体を避ける）** |
| パスワード・APIキー・認証情報 | ✗ | ✗ | ✗ |

セキュリティ上の弱点の技術詳細とは「どこに・どういう不備があるか」が特定できる記述（該当箇所・不備の種類・未対策の範囲など）を指す。**診断や監査プロジェクトの存在・スケジュール・契約形態は対象外**（これらは社内メモに書いてよい）。

書き方: 論点があること・未解決の状態・当日話題に出る見込みだけを残し、技術内容は書かずに一次情報（議事録ツールの該当箇所等）へのポインタを添える。

```
- **★未解決の指摘事項が1件あります（技術内容は本ファイルに記載しません）**: …状態と当日の扱いだけ記載…
  - ※ 技術内容そのものはここに記録していません（機密性の高い技術詳細は記録しないため）。中身の確認は議事録ツールの該当アクションアイテムを直接参照してください
```

チェックリストや「情報が不足している点」など**別セクションに同じ内容が漏れていないか**も確認する（本文だけ伏せても、チェック項目に不備の種類が残ると意味がない）。

### 情報源カバレッジ表（社内メモの末尾に必須）

散文の「収集できなかった情報源」だけで済ませない。**手順4の情報源すべてを1行ずつ**、下の3列で書く。

| 情報源 | 実行したこと | 結果 |
|---|---|---|
| 議事録ツール | 会社名で検索 | 0件 |
| チャット | 会社名で検索 | 2件（自動通知のみ） |
| メール | ドメインで検索 | 1件 |
| 手元のファイル | 会社名で検索 | 5件 |
| 顧客台帳・タスクDB | 検索 | 0件 |
| Web | 公式サイト・ニュース検索 | 会社概要＋直近6件 |

**「実行したこと」列を空欄にしない。** 実行していないなら結果列ではなく実行した列に **「未実行」と理由** を書く。散文だと「収集できなかった」が誠実な申告に見えてしまい、**実際には一度も試していない**ケースが検出できなくなる（過去に複数の資料でこれが起きたことがある）。

この表の下に、確度が低い点・推測にとどまる点を散文で補足する。

## Gotchas（全MTGタイプ共通で過去にハマったケース）

1. **メールアドレスや招待者の一致だけで「同一人物」と断定しない**: カレンダー招待アドレスが一致しただけの別人の議事録を、面談相手の準備資料に転載した事故がある。人物の同定に確証がなければ「未確認」と明記し、議事録を引用する前に参加者が本人かを確認する。憶測で人物欄を埋めない
2. **メッセージは「誰が書いたか」と「誰が言及されているか」を必ず区別する**: 準備対象メンバーの情報収集中に、「そのメンバーについて別の人が書いた投稿」を「本人の発言」と誤読した事故がある。引用前に必ず送信者を確認し、言及と本人発言を混同しない
3. **同席者の所属は名前の並びだけで判断しない**: カレンダー招待の並びから、自社側の外部協力者（業務委託のメンバー等）を先方の同行者だと誤認しかけたケースがある。肩書き・招待元を確認してから「お立場の確認」等をご確認事項に入れる
4. **記録の不在・記録のトーンから悪い方に断定しない**: 過去メールの督促が事務的に固いだけで「関係が険悪」と書かない。社内記録に無い人物は「素性不明」ではなく、担当者個人の人脈という可能性もある。ネガティブ判定・出自不明扱いを資料に書く前に1問確認する。本人が「もう解決した」「気にしなくていい」と言った論点も、次の資料で蒸し返さない
5. **ツールの認証エラー・警告だけで情報源を諦めない**: 「使えない」という警告文が出ても、実際には別の経路（別ログイン、Web版、アプリ版）なら使える場合がある。警告が出たら代替経路を1回試してから「使えなかった」と書く（手順4のツールを1回実行してから判断する）
6. **「社外秘だから社内メモに書けばいい」で機密性の高い技術詳細を書かない**: 対外共有の可否と保存・記録してよいかは別ルールで、後者のほうが厳しいことがある。機密性の高い技術詳細を社内メモに書いてしまい、そのファイル自体を保存・共有できなくなった例がある。線引きと書き方は上の「社内メモにも書いてはいけないもの」を参照

### Gotchas（1on1で過去にハマったケース）

1. **キャリアの選択肢は1本に絞らない**: 本人の職種・志向に応じて複数の成長ルートを併記する。特定の一本道（例: 特定スキルへの特化）に絞ると、本人の志向とミスマッチが起きることがある
2. **メンバーファイルの「メモ・気づき」は1on1直前に必ず読む**: 観察ログが新鮮なほど深掘り質問が刺さる
3. **アジェンダの上司発言は3割以内**: テンプレ通りタイムボックスを切らないと、ついアドバイスしすぎて「業務確認会」になる（Andy Grove / The Coaching Habit原則）
4. **「最近どう？」はオープニング質問として使わない**: 雑談に流れるか「ぼちぼち」で終わって視座が上がらない。代替は四半期初回なら「次の3ヶ月で何ができたら最高？」、通常回はチェックイン（コンディション10点満点）→定型質問の順で必ず入る構造にする

# reply-draft — 返信の下書き（メール・チャット）

受信メールへの返信を、種類ごとの型で下書きする。チャット（Slack／Teamsなど）の未返信には、短い返信文の案も作れる。inbox-triage（このパック）が洗い出した未返信の中から、下書き・返信文の案が欲しいものを個別に頼むときにも使う。

**メールは送信しない。チャットは投稿しない。** どちらも文面の案を作って提示するところまでが仕事。送信ボタン・投稿ボタンは必ず自分で押す。「送って」「OK」と言われても、文面を提示したところで止める。

## 使い方

`$ARGUMENTS` にモードのヒントと対象を書く。

```
/reply-draft [◯◯さんのメール]に返信          → 一般返信
/reply-draft リマインド [MTG名]               → 会議前のリマインド
/reply-draft フォロー [MTG名・顧客名]          → 会議後のお礼・フォローアップ
/reply-draft リスケ [対象]                    → 日程調整・リスケ
/reply-draft 紹介対応 [紹介者名]               → 紹介・つなぎ
/reply-draft [チャットのメッセージ]に返信      → チャットへの返信文
```

## モード判定

| 引数・文脈の手がかり | モード |
|---|---|
| 返信対象のメール・スレッドを指定した一般の依頼 | 一般返信（メール） |
| 「リマインド」「明日の確認」 | 会議前のリマインド（メール） |
| 「フォロー」「お礼」「さっきの」（会議のあと） | 会議後のお礼・フォローアップ（メール） |
| 「日程調整」「リスケ」「予定変更」「候補日」 | 日程調整・リスケ（メール） |
| 「紹介」「紹介いただいた」「紹介御礼」 | 紹介・つなぎ（メール） |
| Slack／Teamsなど、チャットのメッセージへの返信依頼 | チャットへの返信文（下記「チャットへの返信文」） |
| 不明 | どのモードか確認してから進める |

メールの5モードの詳しい手順と文面の型は [references/reply-templates.md](references/reply-templates.md) を参照する。

## チャットへの返信文（軽いモード）

チャット（Slack／Teamsなど）の未返信メッセージに、短い返信文の案を作る。メールの下書きとは違い、宛先・件名は無く、**本文（返信文）だけ**を出す。

1. 対象メッセージ・スレッドを特定する（引数や文脈から。複数候補があれば確認する）
2. スレッドを読み、聞かれていること・期待されている反応をつかむ
3. 短く、そのチャットの他の発言と同じトーンで返信文を作る（メールのような宛名・署名は付けない）
4. **社外の人が見える・参加している場所（外部共有チャンネル・ゲストがいるチャンネルなど）では、社内の事情・金額・契約条件を書かない。** 迷ったら書かない
5. 返信文だけを提示する

**投稿はしない。** 文面の案を作って提示するところまでが仕事で、実際に送る操作は自分が行う。

## 下準備（メールの5モード共通）

1. **接続先を確認する**: 下書きを作るメールアカウントが、自分の普段使っている業務用アカウントであること。個人用アカウントなど別のアカウントに繋がったまま対外文面の下書きを作らない
2. **対象メールを特定する**: 引数や文脈からスレッドを検索する。複数候補が出たら、曖昧なまま下書きを作らず候補を提示して確認する。人に確認できない場面（定期実行など）では、絞り込めないものは下書きを作らず「要確認」として理由を残す
3. **全文を読む**: 要約だけで判断せず、本文を開いて質問・依頼・期限を把握する
4. **文体を合わせる**: `context/owner/profile.md` に署名・文体の指定があれば読んで合わせる。相手との過去のやり取りや `context/clients/<相手先>.md` のカルテがあれば、呼び方・距離感の参考にする（どちらも無ければそのまま進め、その旨を出力に一言添える）

## 出力形式（メールの5モード）

チャットへの返信文モードの出力は、上の「チャットへの返信文」を参照（宛先・件名は無し）。メールの5モードはこの順で提示する。

1. 宛先（To／CC）
2. 件名
3. 本文（プレーンテキスト。Markdown記法・装飾記号は使わない）

下書き保存の機能が使えるメールツールなら、そこに下書きとして保存してから場所を伝える。使えない・繋がっていない場合は、宛先・件名・本文をそのまま提示する。

控えを残したい場合は `work/mail/YYYYMMDD_reply_<テーマ>.md` に保存する（CLAUDE.mdに別の保存先指定があればそちらを優先。`work/mail/` が無ければ作成する）。**ファイル名に相手の会社名・氏名は入れない。**

## 使い分け

| 場面 | 使うもの |
|---|---|
| 受信箱の未返信を洗い出す | inbox-triage（このパック） |
| 返信メールを下書きする／チャットの返信文を考える | このスキル |
| 打ち合わせの記録を残す | meeting-notes（このパック） |

## 守ること

- **送信・転送・予約送信はしない**。送信は自分がメール画面で行うと伝える
- 本文はプレーンテキストのみ
- 宛名・署名の書き方は `context/owner/profile.md` の指定に従う。指定が無ければ、初回の相手には会社名＋氏名＋様、やり取りが続いている相手には直近のメールで自分が呼ばれている形に合わせる
- 自社の正式名称（法人格の位置・略称の有無など）を、`context/company/overview.md` 等で一度確認してから書く
- 金額や契約条件の内訳、社内限定の評価やメモは本文にも件名にもファイル名にも書かない
- 断定できない内容（金額・受諾／辞退・可否など）は、その場で結論を書かない。「確認のうえ、改めてご連絡いたします」の一次回答に留め、必要なら「【要確認: 金額】」のように穴埋めにして、未確定の箇所がひと目でわかるようにする
- 謝罪や催促への返信は、お詫び＋状況確認中＋改めて連絡、に留める。原因や再発防止の具体策など、まだ決まっていない約束をその場で書かない
- 交渉中の内容に返信するときは、今回のやり取りに関係する点だけに絞る。社内で検討した他の論点まで全部書き出さない
- 日程の候補・確定は、カレンダーの空き枠を実際に取得してから書く（架空の候補を作らない）。書式は1行1日「M/D(曜) 10:00〜11:00／14:00〜15:00」。表・おすすめマーク・補足は付けない
- 人物の特定をメールアドレスの一致だけで断定しない
- **パスワード・APIキーなどの認証情報は読まない・書かない**（メールに貼られていても、本文や控えのファイルに写さない）
- ツールが繋がっていない場合は黙って進めず、「使えなかった」と書くか、必要な情報を貼ってもらう

## Gotchas（過去にハマったケース）

1. **接続先を確認せずに下書きを作ると、個人アカウントに対外文面が残ることがある**: 業務用・個人用の両方のアカウントに繋がっている環境で、確認しないまま下書きを作ると、思わぬアカウントに相手向けの文面が残ってしまう。下書きを作る前に接続先を必ず確認する
2. **下書きの本文を直すとき、既存の下書きをそのまま編集すると元のメールとの紐づけが外れることがある**: ツールによっては、一度保存した下書きの本文を編集で差し替えると返信元スレッドとの関連付けが切れ、送信時に相手には無関係の新規メールとして届くことがある。本文を直したいときは、返信操作からもう一度作り直すのが安全（古い下書きは削除する）
3. **自社の社名表記を毎回間違えると、それだけで信用に関わる**: 「株式会社」の前株・後株、正式名称と略称など、自社の名前は一度思い込みで書くと定着してしまう。`context/company/overview.md` 等の正式表記を都度確認する
4. **要判断の内容ほど、下書きで先に答えを書いてしまいやすい**: 金額や可否などまだ決まっていないことを「早く返信したい」気持ちから下書き段階で書いてしまうと、そのまま送られるリスクが上がる。決まっていないことは決まっていないまま下書きにする
5. **相手から届いた会議のURL・ID・パスコードを、そのまま返信本文に書き戻さない**: 承諾の返事なら「承知いたしました」の一言で足りる。接続情報を引用し直す必要はない
6. **日程候補は表や補足をつけず、素のフォーマットで出す**: 表・状況列・おすすめマーク・注釈をつけると、かえって候補が読み取りにくくなる。1行1日の素のフォーマットを崩さない
